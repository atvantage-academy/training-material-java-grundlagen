Gleichheit und Beziehungen modellieren

Gleichheit und Beziehungen modellieren

Als Entwickler:in möchte ich, dass zwei Objekte mit derselben fachlichen Identität als gleich gelten und sich lesbar ausgeben lassen, damit Suchen, Vergleiche und Ausgaben verlässlich funktionieren.

Lernziele

Die Lernenden…

  • überschreiben toString für eine lesbare Objektausgabe.
  • überschreiben equals und hashCode konsistent auf Basis der fachlichen Identität.
  • drücken die Beziehung zwischen zwei Objekten über eine Referenz aus.

Definition of Done

  • Customer und Account besitzen ein aussagekräftiges toString.
  • equals und hashCode von Customer basieren auf der id.
  • Ein Account hält eine Referenz auf seinen Customer-Inhaber.
  • Ein HashSet<Customer> erkennt zwei Objekte mit gleicher id als dasselbe Element.
  • Du hast die Reflexionsfragen schriftlich beantwortet.

Arbeitsschritte

toString überschreiben

Gib eine lesbare Darstellung zurück (z. B. Customer[id=…, name=Alice, city=Hamburg]).

Hinweis: Die meisten IDEs können toString, equals und hashCode generieren — nutze das, aber lies das Ergebnis bewusst.

equals und hashCode auf der id aufbauen

Zwei Kunden sind gleich, wenn ihre id gleich ist — unabhängig von Name/Stadt.

@Override
public boolean equals(Object o) {
  if (this == o) return true;
  if (!(o instanceof Customer other)) return false;
  return this.id.equals(other.id);
}

@Override
public int hashCode() {
  return Objects.hash(id);
}

Gleichheit im HashSet prüfen

Lege zwei Customer mit derselben id in ein HashSet und prüfe die Größe.

Hinweis: Ohne konsistente equals/hashCode enthält das Set zwei Einträge — mit korrekter Umsetzung nur einen.

Reflexionsfragen

  • Warum sollte die Gleichheit auf einer stabilen id beruhen und nicht auf veränderlichen Feldern wie dem Namen?
  • Was passiert in einer HashMap, wenn hashCode zweier gleicher Objekte unterschiedlich ist?
  • Ist die Beziehung Konto→Inhaber eine Assoziation oder eine Komposition? Begründe.
