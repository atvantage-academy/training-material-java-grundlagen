Ein generisches Repository bauen

Ein generisches Repository bauen

Als Entwickler:in möchte ich Kunden und Konten mit derselben, typsicheren Verwaltungslogik ablegen, damit ich Speicher-Code nicht für jeden Typ dupliziere.

Lernziele

Die Lernenden…

  • definieren eine generische Klasse/ein Interface mit Typparameter.
  • schränken einen Typparameter mit extends ein.
  • verwenden das generische Repository typsicher für zwei Typen.

Definition of Done

  • Es gibt ein generisches Repository<T extends Identifiable> mit save(T) und findById(String).
  • Intern speichert es die Elemente in einer Map<String, T> (ID → Element).
  • Es existieren ein Repository<Customer> und ein Repository<Account> ohne duplizierten Code.
  • Die Verwendung kommt ohne explizite Casts aus.
  • Du hast die Reflexionsfragen schriftlich beantwortet.

Arbeitsschritte

Das generische Repository definieren

Führe einen Typparameter T ein und schränke ihn auf Identifiable ein.

public class Repository<T extends Identifiable> {
  private final Map<String, T> items = new HashMap<>();

  public void save(T item) {
    items.put(item.getId(), item);
  }

  public T findById(String id) {
    return items.get(id);
  }
}

Hinweis: Nur wegen der Schranke extends Identifiable darfst Du innen item.getId() aufrufen.

Für zwei Typen verwenden

Erzeuge je ein Repository für Kunden und Konten und speichere/lies Objekte.

Repository<Customer> customers = new Repository<>();
customers.save(alice);
Customer found = customers.findById(alice.getId()); // kein Cast nötig

Hinweis: Beobachte, wie die IDE beim falschen Typ (customers.save(account)) schon vor dem Ausführen meckert — das ist Typsicherheit zur Compile-Zeit.

Reflexionsfragen

  • Was wäre der Nachteil eines Repositories, das intern Object speichert?
  • Warum brauchst Du die Typschranke extends Identifiable — was ginge ohne sie nicht?
  • An welcher anderen Stelle im Banking-System würde sich ein generischer Typ noch lohnen?
