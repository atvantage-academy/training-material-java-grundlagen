Kapselung und Validierung durchsetzen

Kapselung und Validierung durchsetzen

Als Entwickler:in möchte ich, dass Kunde und Konto niemals in einen ungültigen Zustand geraten, damit ich mich im restlichen Programm auf gültige Objekte verlassen kann.

Lernziele

Die Lernenden…

  • deklarieren Felder private und steuern den Zugriff über Getter/Setter.
  • validieren Eingaben in Konstruktor und Settern und lehnen ungültige Werte ab.
  • begründen, welche Prüfungen in die Klasse gehören.

Definition of Done

  • Alle Felder von Customer und Account sind private.
  • Der Konstruktor lehnt null-Werte für Pflichtfelder ab.
  • setName (o. ä.) verhindert null bzw. leere Werte.
  • Der Kontostand kann nicht direkt von außen gesetzt werden (kein öffentlicher Setter dafür).
  • Du hast die Reflexionsfragen schriftlich beantwortet.

Arbeitsschritte

Felder privat machen

Stelle sicher, dass alle Felder private sind. Biete nur dort Getter/Setter an, wo Zugriff wirklich nötig ist.

Hinweis: Nicht jedes Feld braucht einen Setter. Der Kontostand ändert sich nur über Ein-/Auszahlungen — nicht über einen freien Setter.

Pflichtfelder im Konstruktor prüfen

Wirf eine Ausnahme, wenn ein Pflichtwert fehlt, sodass gar kein ungültiges Objekt entstehen kann.

public Customer(String name, String city) {
  this.name = Objects.requireNonNull(name, "name darf nicht null sein");
  this.city = Objects.requireNonNull(city, "city darf nicht null sein");
  this.id = UUID.randomUUID();
}

Setter validieren

Lass den Setter für den Namen null (und optional Leerstrings) ablehnen, bevor er den Wert übernimmt.

Hinweis: Prüfe zuerst, übernimm dann. So bleibt bei ungültiger Eingabe der alte, gültige Wert erhalten.

Reflexionsfragen

  • Welche Zusicherung gibst Du dem Rest des Programms, wenn der Konstruktor keine ungültigen Objekte zulässt?
  • Warum ist ein fehlender Setter manchmal die bessere Entwurfsentscheidung als ein vorhandener?
  • Was spricht dafür, die Validierung in der Klasse statt in jedem Aufrufer zu wiederholen?
